# C00 — Guards

## Goal

Four small programs that make "done" a check instead of a judgement, plus a
Makefile and a CI workflow. Every later chunk's acceptance depends on these, so they
are built first and tested hardest.

## Read first

- `docs/TESTING.md` sections 4 and 6.
- `docs/ARCHITECTURE.md` section 2 (layout, layer rules, build flavours).
- `docs/chunks/TEMPLATE.md` (the spec format these programs parse).

The point: a person (or the next agent) always starts from one file, `NEXTSTEPS.md`, and it is always
current because the agents' own handoff notes feed it. Each agent writes only its **own** file, so parallel

9. **Handoff notes.** Every chunk has `docs/chunks/CNN.done.md`, created from `docs/chunks/DONE-TEMPLATE.md`.
   The agent creates it **first** with `status: in-progress` (this claims the chunk) and finishes it last.
   Front matter: `chunk`, `status` (`in-progress`, `done`, `partial`, `blocked`), `date` (`YYYY-MM-DD`), `agent`,
   `branch`, `cost_usd` (optional number), `unmet` (list of strings: matrix IDs or acceptance items not satisfied),
   `spec_changes`, `decisions`, `next` (lists of one-line strings). Body headings: `## Built`, `## Deviations`,
   `## Surprises`, `## Notes for the next agent`. Unknown front-matter keys are ignored.
10. **`nextsteps check CNN`** fails (exit 1, one problem per line) unless: the file exists (the message names
    `docs/chunks/DONE-TEMPLATE.md`); the front matter parses and `chunk` equals `CNN`; `status` is `done`,
    `partial`, or `blocked` (not `in-progress`); `date` is a valid date; `status: done` has an empty `unmet`;
    `partial` has a non-empty `unmet`; `blocked` has non-empty `unmet` and non-empty `## Surprises`;
    `## Built` and `## Notes for the next agent` each have at least 20 non-space characters; no `TODO:` remains
    anywhere; and every `unmet` entry shaped like a matrix ID names a row that exists in the spec.
11. **`nextsteps build`** reads every spec's front matter (`chunk`, `title`, `depends`) and every `*.done.md`, and writes
    `NEXTSTEPS.md` deterministically (chunks sorted by id, no timestamps other than the dates in the notes, LF line
    endings, a final newline). Sections, in order:
    - a first line `<!-- GENERATED by go run ./scripts/nextsteps build; edit only inside the human block -->`, the title,
      and one sentence telling the reader to read `AGENTS.md` and do the first item under **Start here**;
    - **Start here**: `In progress`, `Needs attention first` (any `partial` or `blocked` chunk), `Ready now (safe to run
      in parallel)`, and `Waiting on` (each remaining chunk with its unmet dependencies), then the two-step claim and
      finish procedure;
    - **Status**: a table with chunk, title, status, depends on, date, and cost;
    - **What the last chunks did**: the first paragraph of `## Built` for the three most recently dated notes;
    - **Notes for the next agent**: the `## Notes for the next agent` text of every `done` chunk that is a direct
      dependency of an in-progress, needs-attention, or ready chunk, each under its chunk id;
    - **Spec corrections to apply**, **Decisions to record**, and **Unmet rows and follow-ups**: every `spec_changes`,
      `decisions`, and `unmet`/`next` entry from every note, grouped by chunk;
    - **Cost**: the total of `cost_usd`;
    - a **human block** between `<!-- human:start -->` and `<!-- human:end -->`, preserved byte for byte across rebuilds
      (created with a short placeholder if missing). This is where the human leaves instructions for the next session.
12. **Statuses.** A chunk with no note is `todo`. Otherwise its status is the note's, except a `done` note with a
    non-empty `unmet` is shown as `partial`. A chunk is **ready** when it is `todo` and every chunk in its `depends` is
    `done`. A `partial` or `blocked` dependency makes its dependents not ready.
13. **Errors.** A note that does not parse, a note for a chunk with no spec, a dependency on an unknown chunk, and a
    dependency cycle are errors: `build` exits 1 naming each, and writes nothing.
14. `nextsteps build --check` exits 1 if `NEXTSTEPS.md` differs from what `build` would write. `accept` does **not** run it
    (parallel branches would otherwise conflict on the generated file); CI does, on `main`, through the workflow below.
15. **Keeping it fresh.** `.github/workflows/nextsteps.yml` runs on every push to `main`, runs `nextsteps build`, and commits
    `docs: update NEXTSTEPS` if the file changed. On a branch, an agent may run `build` before it finishes; if two branches
    both changed the file, the merge conflict is resolved by regenerating it.

Command contracts:

```
matrixcheck <spec.md> <pkg>...     exit 0 ok; exit 1 problems (printed, one per line); exit 2 usage or I/O error
linecount <spec.md>                exit 0 ok; exit 1 over budget; exit 2 usage or I/O error
importcheck [-root dir]            exit 0 ok; exit 1 violations; exit 2 error
accept <CNN> [-from step]          exit 0 all steps pass; exit 1 a step failed; exit 2 error
nextsteps build [--check]          write NEXTSTEPS.md; with --check, exit 1 if it is stale
nextsteps check <CNN>              validate docs/chunks/CNN.done.md; exit 0 ok; exit 1 problems; exit 2 error
```

## Behaviour

1. **Spec parsing.** Front matter is YAML between the first two `---` lines. A row is
   any Markdown table line in the section that starts at a line beginning with `## Matrix` and ends at
   the next line beginning with `## ` whose first cell is an ID. Headings are recognised only at the
   start of a line, so prose that mentions `## Matrix` is not a heading. Header and separator rows are ignored.
   Rows outside the Matrix section are ignored.
2. **Duplicate IDs** in one spec are an error.
3. **matrixcheck** lists tests with `go test -list '.*' <pkg>...` (including packages'
   `_test.go` files and any build tags passed through `-tags`). A test satisfies a row if
   its name, split on `_`, contains the ID as a whole component. Subtests do not count;
   the top-level `TestXxx` function name must carry the ID.
4. matrixcheck fails if any row ID has no satisfying test, **or** if a test name
   contains a component that looks like an ID (`^[A-Z]{2,4}[0-9]{2,3}$`) and is
   not in the spec. (A test may cite several IDs.)
5. **linecount** counts, per package listed in `budgets`, the lines of non-test `.go`
   files, excluding blank lines and lines that contain only a comment. A package over
   budget fails. A package in `packages` with no budget is an error.
6. **importcheck** loads every package with `go list -deps -json ./...` (and again with
   `-tags notui`) and enforces:
   a. the layer rules in `ARCHITECTURE.md` section 2;
   b. no package other than `./tui/...` and `./bundled/...` imports a path beginning
      `charm.land/` or `github.com/charmbracelet/`, in non-test **or** test files;
   c. nothing outside `./tui/...` and `./bundled/...` is reachable only through them
      (checked by building with `-tags notui`);
   d. every third-party module is in the **allowed-imports table**, which is data at the top of the file:
      one line per module naming the packages allowed to import it. The initial table: `gopkg.in/yaml.v3`
      (any non-UI package), `github.com/spf13/cobra` (`./cmd/nova`), `golang.org/x/net/html`
      (`./bundled/webfetch`), and the charm modules, `charm.land/...` and `github.com/charmbracelet/...`
      (`./tui/...`, `./bundled/...`, with `charm.land/fang` also in `./tui/cli`). A violation message names
      the module, the package, and says to record the addition in `docs/DECISIONS.md` (D46).
7. **accept** runs, in order, stopping at the first failure and printing the failing
   command's output: `gofmt -l`, `go vet`, `go build ./...`, `go build -tags notui ./...`,
   `go test -short -race -p 2` on the spec's packages, `go test -race -p 2` on the same,
   `matrixcheck`, `linecount`, `importcheck`, and finally `nextsteps check CNN` (the handoff note must be
   complete). A step whose package does not exist yet is an error, not a skip.
8. `accept` prints a one-line summary per step (`ok`/`FAIL`, duration).

Test strategy: each program has a `run(args, stdout, stderr, env) int` function so tests
call it directly. Fixtures for `matrixcheck`, `importcheck`, and `accept` are small Go
modules written to a temp directory by the test (`testkit` does not exist yet, so use a
local helper). Do not shell out to `go` in a test unless the fixture needs it; ACC tests
may use a stub `go` on `PATH` that records its arguments.

## Fuzz and property tests

| Name | Asserts |
|---|---|
| `FuzzSpecLoad` | `Load` never panics on arbitrary bytes and returns either a spec or an error |
| `FuzzRowID` | the ID regexp accepts exactly the documented shape |
| `FuzzDoneNote` | arbitrary bytes as a handoff note never panic; `check` returns problems or nil |

## Out of scope

- Mutation testing, coverage gating (the Makefile may report coverage; it is not a gate).
- Any code outside `scripts/`, the Makefile, and the workflow.

## Makefile

```
test:       go test -short -p 2 ./...
test-full:  go test -p 2 ./...
race:       go test -race -p 2 ./...
fmt:        gofmt -l .
vet:        go vet ./...
accept:     go run ./scripts/accept $(C)
ci:         fmt vet build build-notui race importcheck matrixcheck-all linecount-all nextsteps-check
nextsteps:  go run ./scripts/nextsteps build
```

`matrixcheck-all` and `linecount-all` loop over every spec in `docs/chunks/` whose
packages exist and run the programs. A spec whose packages do not exist yet is skipped
in `ci` (and nowhere else).
